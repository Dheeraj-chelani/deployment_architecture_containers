# ProShop Containerized Deployment Architecture

A containerized deployment of the Django-based **ProShop** application
using Docker Compose, Nginx, and MySQL. Two Django/Gunicorn application
containers run behind Nginx, which distributes incoming requests across
the web containers and serves shared static and media files.

## Architecture

``` text
                         Client / Browser
                                |
                         http://HOST:8080
                                |
                         Nginx (port 80)
                         /              \
                   web1:8000          web2:8000
                  Django +            Django +
                  Gunicorn            Gunicorn
                         \              /
                          \            /
                           MySQL (db:3306)

          Shared Docker volumes:
          - db-data      -> MySQL database files
          - static-data  -> Django collected static files
          - media-data   -> uploaded media files
```

### Request flow

1.  A client sends an HTTP request to port `8080` on the host.
2.  The Nginx container listens on port `80` and uses the
    `django_backend` upstream to distribute application requests between
    `web1` and `web2`.
3.  Each Django application runs through Gunicorn on port `8000`.
4.  Both web containers connect to the MySQL service using the Compose
    service name `db` on port `3306`.
5.  Nginx serves `/static/` and `/media/` from the shared Docker
    volumes.

> **Note:** The Nginx upstream uses a basic two-server load-balancing
> configuration. This setup is intended for learning and local
> deployment; it is not, by itself, a highly available production
> architecture.

## Technology Stack

-   **Django** --- web application framework
-   **Python 3.12** --- application runtime
-   **Gunicorn** --- WSGI application server
-   **Nginx** --- reverse proxy and load balancer
-   **MySQL 8.0** --- relational database
-   **Docker** --- containerization
-   **Docker Compose** --- multi-container orchestration
-   **Vagrant + VirtualBox** --- local virtual machine environment
-   **Ubuntu 24.04** --- Vagrant base box

## Prerequisites

-   VirtualBox
-   Vagrant
-   Docker Engine
-   Docker Compose plugin (`docker compose`)
-   Git and network access to clone the application repository during
    the Docker image build

The supplied `Vagrantfile` defines an Ubuntu 24.04 VM with `2 GB` RAM, a
private IP of `192.168.56.16`, and a forwarded guest port `80` to host
port `8080`. It does **not** automatically install Docker or Docker
Compose; install and verify them inside the VM before starting the
containers.

## Configuration

Create a `.env` file in the same directory as `docker-compose.yaml`. Use
your own strong, unique values:

``` dotenv
SECRET_KEY=replace_with_a_long_random_django_secret
DB_USER=proshop_user
DB_PASSWORD=replace_with_a_strong_database_password
MYSQL_ROOT_PASSWORD=replace_with_a_strong_root_password
```

Keep `.env` private. Do not commit real passwords or Django secret keys
to GitHub. If a real secret has already been committed, rotate it.

The Compose configuration sets `DEBUG=False`, database name
`proshop_db`, and database host `db`. The configured allowed hosts
include `localhost`, `127.0.0.1`, and `192.168.56.16`; CSRF trusted
origins include the local HTTP addresses shown in the Compose file.
Update these values if your access hostname or IP changes.

## Run the Project

Run these commands from the project directory, where
`docker-compose.yaml` and `.env` are located.

### 1. Start the Vagrant VM (if using the provided VM)

``` bash
vagrant up
vagrant ssh
```

Inside the VM, ensure Docker Engine and the Docker Compose plugin are
installed and running. The Vagrantfile alone does not install them.

### 2. Build and start the containers

``` bash
docker compose up --build -d
```

This builds the `web1` application image and starts the MySQL, `web1`,
`web2`, and Nginx services. The `web2` service uses the same application
image as `web1`.

### 3. Check service status and logs

``` bash
docker compose ps
docker compose logs -f
```

To inspect an individual service:

``` bash
docker compose logs -f nginx
docker compose logs -f web1
docker compose logs -f web2
docker compose logs -f db
```

### 4. Open the application

-   Through the forwarded host port: `http://localhost:8080`
-   From a machine that can reach the VM's private network:
    `http://192.168.56.16:8080` only if the service/host networking
    exposes that port as configured. Otherwise, use the actual host
    address and forwarded port.

The Compose file also maps `web1` to host port `8001` and `web2` to
`8002` for debugging. These are direct application access ports, not the
normal Nginx entry point.

### 5. Stop the project

``` bash
docker compose down
```

To stop the containers and also delete the named database, static, and
media volumes:

``` bash
docker compose down -v
```

**Warning:** `docker compose down -v` deletes the persistent volumes,
including the MySQL data stored in `db-data`. Back up data first if it
matters.

                                                            Django/Gunicorn
                                                            application

                                                            reachable
                                                            internally as
                                                            `db:3306`

The `web1` and `web2` host-port mappings are marked for debugging in the
Compose file. For a more locked-down deployment, remove those published
ports and route external traffic only through Nginx.

## Nginx Configuration

The `nginx/nginx.conf` file defines an upstream named `django_backend`
with two backend servers:

``` nginx
upstream django_backend {
    server web1:8000;
    server web2:8000;
}
```

The main location proxies requests to that upstream and forwards headers
such as `Host`, `X-Real-IP`, `X-Forwarded-For`, and `X-Forwarded-Proto`.
Static and media paths are served from the shared volumes mounted into
Nginx.

## Docker Image Notes

The supplied Dockerfile:

-   Uses `alpine/git` as a build stage to clone the ProShop source
    repository.
-   Uses `python:3.12-slim` for the application image.
-   Installs build dependencies needed for `mysqlclient`.
-   Installs the Python requirements and Gunicorn.
-   Runs `python manage.py collectstatic --noinput` during image build.
-   Starts Gunicorn with three workers, bound to `0.0.0.0:8000`.

Because the source is cloned during the image build, rebuilding can
retrieve the latest default-branch commit from the configured
repository. For reproducible builds, pin the source to a specific commit
or build from a local, version-controlled source checkout.

## Persistent Data

Docker Compose defines three named volumes:

-   `db-data` --- MySQL database files
-   `static-data` --- collected Django static files shared by the web
    containers and Nginx
-   `media-data` --- media files shared by the web containers and Nginx

Named volumes persist when containers are recreated, unless they are
explicitly removed. Keep separate backups for important data.

## Database Backup

A SQL file named `proshop_20260823_152502.sql` appears in the project
directory. If it is a valid dump for this database, it can be imported
after the MySQL service is healthy. Review the dump and make a backup
before importing. Example:

``` bash
docker compose exec -T db sh -c 'exec mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE"' < proshop_20260823_152502.sql
```

This command assumes the dump is compatible with the configured database
and that the MySQL environment variables are available in the container.

## Troubleshooting

### Check whether containers are running

``` bash
docker compose ps
docker compose logs --tail=100
```

### Check Nginx configuration

``` bash
docker compose exec nginx nginx -t
```

### Check database health and connectivity

``` bash
docker compose logs db
docker compose exec db mysqladmin ping -h localhost
```

### If Nginx returns `502 Bad Gateway`

-   Check that `web1` and `web2` are running.
-   Inspect the web-container logs for Django, Gunicorn, or database
    errors.
-   Confirm that the Nginx upstream names match the Compose service
    names.
-   Confirm that both web containers listen on `0.0.0.0:8000` inside
    their containers.
-   Confirm the MySQL service is healthy and the `.env` credentials are
    correct.

### If static files are missing

-   Confirm `collectstatic` completed successfully during the image
    build.
-   Confirm the `static-data` volume is mounted at `/app/staticfiles` in
    the web containers and Nginx.
-   Check the `STATIC_ROOT` setting in Django.

## Security and Production Considerations

-   Never commit `.env` files, database passwords, or production secret
    keys.
-   Keep `DEBUG=False` and configure `ALLOWED_HOSTS` and
    `CSRF_TRUSTED_ORIGINS` for the actual deployment addresses.
-   Avoid exposing the database publicly.
-   Remove direct host-port publishing for `web1` and `web2` when direct
    debugging access is not required.
-   Use HTTPS/TLS for public deployments.
-   Configure database backups and test restoration.
-   Consider health checks for the web services, resource limits,
    monitoring, and a deployment strategy for image updates.
-   Two web containers behind Nginx do not guarantee high availability
    if the VM, Docker host, or shared database fails.
